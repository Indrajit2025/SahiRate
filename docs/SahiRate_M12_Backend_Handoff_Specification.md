## 1. Introduction

**What SahiRate is:**
SahiRate is a field-ready, offline-first platform designed to connect informal scrap collectors with the formal authorized recycling chain. 
The collector is the center of the system. SahiRate is **not** just a marketplace—it is an operating layer that handles offline lot creation, price discovery, localized audio guidance, verifiable QR-based handovers, and traceability.

**Key Technical Differentiator:** 
*Real offline-first operation.* The application works in poor-connectivity environments. Collectors can create lots, take photos, and process data completely offline. Synchronization happens deterministically when connectivity is restored.

## 4. Core Workflows & State Transitions

### Collector Flow
1. Collector opens SahiRate (even offline).
2. Creates collection lot (material, weight, price, photo).
3. Confirms lot -> Lot stored locally -> Outbox event LOT_CREATED.
4. Online sync pushes event to backend.
5. Recycler sees eligible lot and accepts it.
6. Handover QR generated by Recycler.
7. Collector scans QR, verifies amount, and confirms handover.
8. Recycler completes handover & payment is recorded.

### Recycler Flow
1. Dashboard -> Available lots.
2. Accepts lot -> Accepted Lots / My Lots.
3. Verify lot (enter verified weight/final rate).
4. Generate handover QR.
5. Wait for collector confirmation.
6. Complete handover.
7. Record payment.

### Admin Flow
Currently mocked via /admin (Transactions, Verification, Alerts, Audit).
Backend must supply endpoints to replace deterministic demo states.

### Lot State Machine (Server-Side Enforcement)
The backend must enforce valid state transitions. Never trust the frontend completely.

AVAILABLE -> ACCEPTED -> VERIFIED -> QR_GENERATED -> COLLECTOR_CONFIRMED -> COMPLETED

**Invalid Transitions to Prevent:**
* Accepting an already ACCEPTED lot.
* Completing a handover before COLLECTOR_CONFIRMED.
* Recording payment before completion.
* Changing ownership without authorization.

## 5. Database Architecture (Proposed PostgreSQL Schema)

Prefer PostgreSQL (+ PostGIS for location logic). 

**Key Tables:**
* `users` (id UUID, phone, password_hash, role, created_at)
* `collector_profiles` / `recycler_profiles` (user_id UUID FK, location_geom, verified_status)
* `lots` (id UUID, collector_id UUID FK, material, approx_weight_kg, estimated_value, status, created_at_local)
* `lot_photos` (id UUID, lot_id UUID FK, object_url)
* `lot_acceptances` (id UUID, lot_id UUID FK, recycler_id UUID FK)
* `handovers` (id UUID, lot_id UUID FK, recycler_id UUID FK, final_weight, final_amount, qr_reference)
* `payments` (id UUID, handover_id UUID FK, amount, mode, status, timestamp)
* `audit_events` (id UUID, entity_id UUID, event_type, payload JSONB, actor_id UUID)

> [!TIP]
> Ensure `idempotency_key` or `event_id` is stored to prevent duplicate outbox processing.

## 7. Offline Sync API Contract

This is the most critical integration point. The frontend outbox will send queued events to the backend.

### POST `/api/v1/sync/events`
* **Purpose:** Ingest offline events (e.g., LOT_CREATED).
* **Request Body:** Array of events.
  ```json
  {
    "events": [
      {
        "event_id": "uuid-1234",
        "type": "LOT_CREATED",
        "entity_id": "lot-uuid",
        "payload": { "material": "plastic", "weight": 10 },
        "created_at_local": "2026-09-12T10:00:00Z"
      }
    ]
  }
  ```
* **Handling Requirements:** 
  * Backend must check `event_id` against processed events (Idempotency).
  * Backend should apply the event to the database.
  * Return success/failure per event so the frontend SyncManager can clear successful events from the outbox.

### GET `/api/v1/sync/changes`
* **Purpose:** Pull latest state from backend (for Recycler dashboards, price updates).

## 9. AI/ML, Price Discovery & Photos

* **AI/ML Integration:** Expose `/api/v1/ai/classify`. Input: Image. Output: `{"material": "PET", "confidence": 0.92}`. Do not fake confidence. Allow manual correction fallbacks.
* **Price Discovery:** The backend must serve live price maps (regional/material). The frontend needs to distinguish between cached prices (offline) and live prices. Do not present fake prices as production data.
* **Photos:** Implement an upload endpoint `/api/v1/photos/upload`. Ensure MIME validation and size limits.
* **Recycler Matching:** Provide explainable matching logic (distance, capacity, rate) rather than a black-box.

## 10. Security Checklist

- [ ] Password Hashing (bcrypt/argon2).
- [ ] JWT Validation on all protected endpoints.
- [ ] SQL Injection protection (use SQLAlchemy ORM).
- [ ] Idempotency keys on state-mutating requests (sync outbox).
- [ ] Ownership checks (Collector can only confirm THEIR handover).
- [ ] CORS properly configured for frontend URLs.
- [ ] Secure secrets via `.env`. No secrets committed.
